# 应用档案测试模板

本指南用于把新的真实应用观察升级为可审计的档案测试。先运行只读计划模板，再为目标应用单独编写测试；不要把别的应用的启动、关闭、selector 或清理逻辑直接复制成“通用能力”。

## 1. 先建立目录事实

先在 `config/app-profiles.json` 中增加唯一 `appId`，只填写已经观察到的版本、进程/宿主、窗口类和 L0–L3 状态。未知写 `not-tested`，未安装写 `not-installed`；不能把“框架看起来支持”写成已验证。

运行计划模板不会启动应用、创建证据或修改仓库：

```powershell
pwsh -NoProfile -File tests/profile-test-template.ps1 -AppId <app-id> -Plan
pwsh -NoProfile -File tests/profile-test-template.ps1 -AppId <app-id> -Plan -Json
```

没有显式 `-Plan`、目录中没有唯一 appId，或输出选项冲突时，模板退出 `2`。它是可执行检查表，不是具备桌面权限的通用测试驱动器。

## 2. 十阶段实现顺序

1. 记录版本、安装来源和验证日期。
2. 运行纯只读 `probe`；发现阶段不得启动、关闭或重启应用。
3. 绑定精确 PID、exe 身份、宿主关系、窗口类和完整性；多候选退出 `2`。
4. 选择最低可靠控制层：优先 L0，再考虑 L1、L2、L3；未知保持未知。
5. 把 before 证据绑定到精确目标，只放唯一临时目录。
6. 只执行有回滚的动作或隔离测试对象，不跨越目录中的停手线。
7. 用独立通道验证；动作 API 返回成功不能单独作为成功判据。
8. 撤回测试状态，只关闭测试自己创建且再次核对身份的目标。
9. 在 `finally` 清理敏感临时证据；清理前验证绝对路径、命名空间、owner 和精确文件名。
10. 共性问题优先进入生产探测、拒绝或契约；易腐事实留在 `app档案.md` 和机器目录。

## 3. 测试文件必须回答的问题

- 如何证明没有复用、关闭或覆盖用户现有实例？
- 写前如何证明目标唯一、版本相符、没有草稿或未保存状态？
- 为什么所选层比下一层更可靠，是否完全避免了 L2？
- 动作如何撤回，异常路径是否也撤回？
- 哪个独立状态、语义读回或业务产物证明动作真正生效？
- 哪些操作属于最终动作，测试如何在输入前拒绝？
- 临时目录边界、清理 owner 和残留检查是什么？
- 哪些原始证据含账号、正文、设备名或路径，如何保证不入库？

## 4. 接入要求

真实测试命名为 `tests/<app-id>-profile.ps1`，加入 `tests/run-tests.ps1` 的 `Profiles` 层，但不得加入默认 Contract 层。`writesInput` 必须反映是否真的写应用状态；只读不是“动作可逆”的别名。

同步更新：

- `references/app档案.md` 的人工事实和失败边界；
- `config/app-profiles.json` 的 `profileStatus`、`testPath`、能力、任务、停手线、最后结果和复验条件；
- `references/应用能力矩阵.generated.md`，只能通过 `scripts/generate-app-matrix.ps1` 生成；
- 受影响的控制面、威胁模型和隐私说明。

最后先运行 `tests/app-profile-catalog-contract.ps1` 和 `tests/profile-template-contract.ps1`，再显式选择真实档案测试。退出 `2` 是安全拒绝或 unknown，绝不能为了得到绿色结果改成成功。
