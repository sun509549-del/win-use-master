# 版本与发布策略

## 版本真相源

`config/release.json` 是版本、通道、发布状态和发布门的真相源；根目录 `VERSION` 只是给工具和用户读取的单行投影，必须与 manifest 完全一致。`CHANGELOG.md` 记录累计变化，`RELEASE_NOTES.md` 描述当前候选。README、文档标题或 Git tag 都不能反向覆盖 manifest。

当前候选是 `0.1.0-beta.1`，状态为 `unreleased`。没有 release tag、发布日期、published commit 或 previous stable；任何文档都不得把它写成已经发布。

## 语义化版本

### v1.0 之前

- `0.MINOR.0`：新增能力，或需要调用方迁移的不兼容命令/默认行为变化；必须在 Changelog 和 Release Notes 中列出迁移说明。
- `0.MINOR.PATCH`：向后兼容修复、文档、测试和不改变公开契约含义的安全加固。
- `-alpha.N`、`-beta.N`、`-rc.N`：同一目标版本的递进候选；编号只增不复用。

0.x 不承诺稳定 API，但也不允许静默破坏。已有 `*-v1` schema 的字段含义不得原地改变；删除字段、改变类型或重解释枚举必须发布新的 `*-vN`。退出码 `0/1/2` 的成功/失败/拒绝或 unknown 含义在 0.x 期间也保持稳定。

### v1.0 及以后

- Patch：修复、文档和不改变公开契约的安全加固。
- Minor：向后兼容的新命令、参数、可选字段或 schema。
- Major：默认行为、命令语义、收据 schema、退出码含义或安全授权模型的不兼容变化。

## 发布门

正式发布必须同时具备：干净 clone、完整 Contract、Desktop/Coordinate 连续两次、当前里程碑真实档案、隐私扫描、目标 SHA 远程 CI、人工证据抽查、Release Notes、可验证 tag 和源码校验和。`passed-local` 只能证明本机阶段，不等于发布通过；`pending`、`blocked`、`unknown` 任一存在时保持 Beta/未发布。

只读检查：

```powershell
pwsh -NoProfile -File scripts/release-check.ps1
pwsh -NoProfile -File scripts/release-check.ps1 -Json -Summary
```

报告是审计汇总，不创建 commit、tag、GitHub Release 或文件，不会把缺失证据推断成通过。

## 候选与发布流程

1. 更新 `config/release.json` 的目标版本，保持 `status=unreleased`，同步 `VERSION`、Changelog 和草案 Release Notes。
2. 从干净 clone 完成所有发布门；每项证据写入 manifest，但本地通过仍标为 `passed-local`，直到目标 commit 的远程证据确认。
3. 固定候选 commit，核对 diff、凭据、许可证、生成文件和临时残留。
4. 只有仓库所有者明确授权发布后，才创建签名 tag；若签名条件不可用，则使用受保护、不可移动的 tag，并在 Release Notes 说明。
5. 对实际分发的源码归档生成 SHA-256；不提交现场构建的 `HuWin.dll`，也不对 GitHub 自动生成且内容规则可能变化的链接伪造稳定校验和。
6. 验证安装命令取得预期 tag、`VERSION` 和 commit，再发布 Release Notes。
7. 发布后 72 小时只处理 P0/P1 回归；其它功能进入下一版本。

发布动作是外部状态变更。完成文档或本地测试不构成创建 tag、Release 或推送的授权。

## Changelog 规则

未发布变化只进入 `[Unreleased]`，按 Added/Changed/Deprecated/Removed/Fixed/Security 组织。发布时创建 `## [x.y.z] - YYYY-MM-DD`，内容来自本次候选；不要重写已发布版本，不把未验证路线图写成已实现，也不把安全细节或原始证据放入 Changelog。
